# 证据驱动探索循环

## 定位

本 Skill 是当前帧的**临时执行协议**，不是项目级模式。它与任务栈正交：

- `campaign-work-stack` 管理任务、分叉、恢复与历史；
- 本 Skill 管理一个知识问题如何通过实验形成足以决策的证据；
- `single-phase-execution-loop` 管理方案已足够明确后的设计、实现与评审。

每个新任务默认走普通执行。只有继续往下做会变成无证据猜测时，才临时进入探索循环。熟悉项目可以全程使用任务栈而一次都不启用本 Skill。

## 阻塞分流

遇到失败或阻塞时，先分类：

| 类型 | 判定 | 动作 |
| --- | --- | --- |
| 实现偏差 | 已知正确方案，只是没实现对 | 留在 Executor 修复或重试 |
| 认知缺口 | 不知道原因、可行性或应选哪条路 | 启用本 Skill |
| 价值决策 | 技术上可做，但成本、风险或什么算“够好”不明 | 向用户呈现选项与证据 |
| 外部阻塞 | 缺权限、账号、数据或外部系统可用性 | 标记 blocked / escalated |

验收证据缺失不一定是认知缺口。已知要跑什么验证、只是还没留存结果时，由 Executor 补取证，不启用探索。

## 启用判据

### 任意一个硬信号即启用

- 技术路线的可行性未知；
- 实现已失败，但真实根因未知；
- 多个可能根因并存，现有证据无法区分；
- 关键选型必须依赖实测，不能只根据文档推断；
- 验收标准需要通过原型或基线才能定义；
- 当前无法给出带依据的下一步，只能随机尝试。

### 两个以上弱信号建议启用

- 使用团队从未接触过的框架、模型或外部系统；
- 同时存在多个看似合理的技术方案；
- 性能或效果高度依赖真实数据；
- 外部行为与文档不完全一致；
- 任务目标包含“调研”“验证”“能否实现”或“试一下”。

任务只是工作量大、涉及文件多或需要评审，不构成探索信号。

## 授权边界

同时满足以下条件时，可在已批准的任务范围内自主运行最小实验：

- 可逆且成本低；
- 不改变外部系统或用户数据；
- 不改变业务成功标准；
- 不新增明显费用、安全、隐私或兼容风险。

出现以下任一情况时，先向用户提交选项、证据和推荐：

- 扩大任务范围或改变验收标准；
- 引入付费资源、新外部服务或高成本计算；
- 修改协议、schema、公共接口或其他高回滚成本设计；
- 实验具有不可逆影响；
- 候选路线代表不同产品、成本或风险取舍；
- 已达到约定的探索预算或停止条件。

用户决定价值、成本、风险和“够好”的定义；代理负责在这些边界内选择信息增益高的技术实验。

## 与任务栈接线

本 Skill **不构成创建任务栈的授权**。

- 已有栈：先 `capture --disposition blocks`，再把知识问题压成当前执行帧的探索子帧并激活；父帧 `suspended`，子帧关闭后自动恢复。
- 没有栈且可单轮收口：可在当前上下文内直接运行循环，不因“探索”自动建栈。
- 没有栈且出现跨会话、多分叉等 `campaign-work-stack` 启用信号：走该 Skill 的 `propose`，只有用户批准后才 `ensure`。

需要在栈帧中记录探索时，读 [references/frame-protocol.md](references/frame-protocol.md)。

## 循环

1. **定义问题与决策**：写清缺哪项知识，以及它将解锁哪个决策。
2. **列出候选假设**：包含至少一个可被证据推翻的假设；不要把实现任务冒充假设。
3. **设计最小区分实验**：优先选择能以最低成本区分多个候选解释的实验，而不是简单地“试一试”。
4. **预先写出判据**：运行前写明哪种观察支持、推翻或无法区分假设。
5. **运行并记录证据**：保留命令、样本、输出、指标或日志的可反查指针。
6. **形成结论并路由**：明确证据支持什么、不支持什么，以及返回 Executor、Designer、用户决策或终态。

开始前设定实验次数、时间、样本或计算成本中至少一项预算。每一轮实验都必须提高对下一步决策的确定性；不得用无限尝试代替停止条件。

## 退出与返回

探索帧的 `done` 不表示“实验跑完了”，而表示“已获得足以决定下一步的证据”。

| 结果 | 路由 |
| --- | --- |
| 证据支持某条实现路线 | `done`，返回父执行帧 / Executor |
| 证据推翻当前设计 | `done`，返回 Designer；受控模式下回计划审批 |
| 出现新假设且仍在预算内 | 继续当前问题的下一轮实验 |
| 证据不足且预算耗尽 | `parked`，写明恢复条件并交给用户 |
| 证明当前路线不可行 | `wontfix` 或切换已批准的候选路线 |
| 发现跨轮缺陷 | `escalated`，立项后保留指针 |
| 需要产品、成本或风险取舍 | 暂停并请用户决策 |

## 单阶段循环接线

Reviewer FAIL 或 Designer / Executor 返回未知根因时：

1. 按“阻塞分流”确认它是认知缺口，不是可直接修复的实现偏差。
2. 暂停原执行路线；探索本身不消耗 Executor retry。
3. 运行探索循环并保留证据。
4. 按结论返回 Executor、Designer 或用户。

本 Skill 不覆盖受控编排的不可变快照和阶段批准权。如果结论要求修改已批准的设计，回计划模式交由用户批准。

## 禁止行为

- 不因任务大、代码多或开发者不熟悉语法就启用探索；
- 不用随机换库、换模型或改参数代替可区分的假设；
- 不在低成本实验可以决定技术路线时，把选择题直接丢给缺少相关经验的用户；
- 不把“命令运行成功”或“代码写完”当作探索结论；
- 不在没有预算、停止条件或对下一步决策无影响时继续实验；
- 不因启用本 Skill 而扩大原任务授权、自动建栈或绕过外部变更批准。
