# 任务失败通俗解释

## 目标

把工程失败报告翻译成用户能理解、能据此做决定的说明。先讲结论，再讲证据；不把推测说成事实，不把部分成功说成整体成功。

## 触发边界

在以下情况使用：

- Reviewer 输出 `FAIL`，阶段或 Goal 进入 `blocked`，无进展暂停，或重试耗尽仍未通过；
- 测试、构建、脚本、部署或外部依赖出现不可恢复错误；
- 用户给出任务 ID、失败报告、日志，询问“为什么失败”“发生了什么”“这个术语是什么意思”。

不要因为一次可恢复的命令非零退出就中断正常执行。读取
`campaign-work-stack/references/output-contract.md`，按可继续、决策/阻塞、交付/恢复选择展示深度；
不是每次 FAIL 都生成完整长报告，也不是只有失败终态才说明重要风险。

## 取证顺序

按以下顺序收集证据，并在报告中标出证据来源：

1. 阅读当前对话中的用户目标、工具输出、测试输出和 Reviewer 原文。
2. 如果用户提供任务 ID，优先读取对应任务的历史摘要或会话记录；无法访问时明确说明，不要猜测历史内容。
3. 在项目内查找该任务绑定的 `execution_plan`、`progress_tracker`、Reviewer YAML、测试产物和 `scratch/` 日志；只读取与该任务相关的文件。
4. 对关键结论做交叉核对：状态、命令退出码、产物是否存在、前后 digest/版本/路径是否一致。
5. 区分四类信息：已确认事实、合理推断、未验证事项、与本次失败无关的背景噪声。

解释阶段默认只读，不修改代码、不创建提交、不自动重跑昂贵测试、不自动部署。

## 失败分类

先判断主因属于哪一类，可同时标注次要原因：

- **实现问题**：代码逻辑、边界条件或配置本身不满足目标。
- **验收/证据问题**：功能可能部分可用，但检查、digest、来源绑定或测试证据不足以证明它正确。
- **环境/资源问题**：依赖、权限、网络、内存、GPU、工具版本等阻止了验证。
- **数据/输入问题**：输入缺失、格式错误、数据冲突或数据质量不足。
- **流程/范围问题**：约束、阶段、重试次数或授权不允许继续。

不要仅凭错误关键词认定为“算法错”；先判断失败发生在哪一层，以及是否真的影响业务结果。

## 分级输出

先用一句话说明失败在哪一层、当前能否继续。其余信息按需要合并为段落或短列表，不强制九段标题。

- **可继续的 FAIL**：原因及证据、通过/未通过部分、影响、剩余重试或预算、下一步。
  已知根因直接说明，未知则标明；同类重复失败只补变化，不重新讲全部背景。
- **阻塞、无进展暂停、额度耗尽或需用户决定**：展开已确认事实与未知、
  直接原因/已知根因、已完成与未完成、实际影响、关键证据及置信度，
  给出少量可选行动、推荐及准确恢复条件。额度说明引用现有记录，不猜剩余次数。
- **用户要求详细解释**：按因果顺序展开关键事件及相关概念，保留证据入口。

影响范围针对实际涉及的代码、数据、环境或后续工作说明；尚未检查的影响写“未验证”，
不能为了报告完整宣称“生产不受影响”。术语会妨碍理解时解释，日常类比仅在有助理解或用户要求时提供，
并让类比对应真实失败机制。

若满足下文“解释后的条件式诊断”，先取得诊断结论，再合并到下一步，不另写一份重复报告。
简报不删完整角色报告、Reviewer YAML 或验证记录，也不隐藏 blocker、高风险、待批准事项和关键未验证项。

## 写作规则

- 先用日常语言，再保留括号中的英文或代码标识，避免连续堆砌缩写。
- 用“系统拒绝继续”“检查没有发现篡改”等可理解的动作描述，少用“链路异常”“契约不满足”这类空泛句子。
- 解释“失败”与“没有证据证明成功”的差别；后者不能自动等同于业务功能错误。
- 区分流程暂停、阶段 blocked 与平台 Goal 实际状态；不能仅因两轮无进展就声称 Goal 已 blocked，
  也不把停止自动尝试说成完成。
- 报告长度以用户能快速读完为准；复杂任务展开证据，不为凑格式重复内容。

## 自动接入编排闭环

当本 Skill 被 `single-phase-execution-loop` 或 `multi-phase-plan-orchestrator` 调用时：

1. 在 Reviewer `FAIL`、重试耗尽仍失败、无进展暂停或阶段 `blocked` 后按级别生成解释；
2. 解释先于下一轮 retry 展示，但不改变机器可读的 Reviewer YAML、retry 计数或状态文件；
3. 若失败可重试，技术动作交给实际接收者（Executor、Designer 或探索入口），用户看到白话摘要；
4. 若重试耗尽仍失败、无进展暂停或确实 blocked，停止相关自动尝试，
   把 blocker、影响、证据与恢复条件交还用户。不得截断已启动最后一轮的正常评审。

## 解释后的条件式诊断

完成事实取证与失败分类后，**自动检查是否需要 `ai-task-triage`**，而不是每次失败都启动完整诊断。
这是主代理读取 Skill 后执行的流程约定，不是后台 hook，也不承诺脱离当前会话自动运行。

满足以下任一情况，且已有分流未给出有证据的下一步时，读取
`ai-task-triage/SKILL.md` 并进行一次只读诊断：

- 仍无法判断下一步应该补信息、做探索、恢复任务状态，还是请求用户决定；
- 连续修复没有取得有效进展，旧路线的依据已不足；
- 发现目标/分支丢失、项目约束遗漏、验收定义不清，原失败分类不足以指导继续。

交接：用户目标与请求范围、已确认事实/未验证项、失败类型、证据指针、已有路由，
以及 retry/预算、阶段审批、暂停或外部阻塞等继续限制。将诊断结果合并到“下一步”，交还原调用者。

- 已知根因且修复动作明确，或编排已确定补验收证据/进入探索等有效路由时，不重复诊断。
- 同一失败、同一证据只诊断一次，内外层编排复用结论；诊断 Skill 不反向调用本 Skill。
- 用户只要求解释时，诊断也止于建议；不得顺势修改代码、建栈或运行实验。
- 重试耗尽仍失败、预算耗尽、无进展暂停、blocked 或待审批时，可以给只读诊断建议，但仍须停止相关自动尝试；
  不以改路由重置计数、重开预算、修改阶段状态或恢复执行。用户明确暂停/停止时不启动新诊断。
- 若诊断 Skill 不可用，保留本报告，说明尚不能完成诊断路由及缺少的能力，不假装已经接入。

## 最低质量门禁

输出前检查：

- 是否引用了实际证据，而不是只复述错误标题？
- 是否区分了业务逻辑失败与验收/证据失败？
- 是否说明了实际影响，未检查的影响有没有标成未验证？
- 是否按理解需要解释关键术语，避免无意义类比？
- 是否明确写出未知信息和下一步？
- 是否保留停止条件、剩余额度和审批边界，没有因简报而隐藏它们？
