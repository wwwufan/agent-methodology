# 任务失败通俗解释

## 目标

把工程失败报告翻译成用户能理解、能据此做决定的说明。先讲结论，再讲证据；不把推测说成事实，不把部分成功说成整体成功。

## 触发边界

在以下情况使用：

- Reviewer 输出 `FAIL`，阶段或 Goal 进入 `blocked`，或重试次数耗尽；
- 测试、构建、脚本、部署或外部依赖出现不可恢复错误；
- 用户给出任务 ID、失败报告、日志，询问“为什么失败”“发生了什么”“这个术语是什么意思”。

不要因为一次可恢复的命令非零退出就中断正常重试；只有达到失败终态，或用户明确要求解释时，才生成完整报告。

## 取证顺序

按以下顺序收集证据，并在报告中标出证据来源：

1. 阅读当前对话中的用户目标、工具输出、测试输出和 Reviewer 原文。
2. 如果用户提供任务 ID，优先读取对应任务的历史摘要或会话记录；无法访问时明确说明，不要猜测历史内容。
3. 在项目内查找该任务绑定的 `execution_plan`、`progress_tracker`、Reviewer YAML、测试产物和 `scratch/` 日志；只读取与该任务相关的文件。
4. 对关键结论做交叉核对：状态、命令退出码、产物是否存在、前后 digest/版本/路径是否一致。
5. 区分四类信息：已确认事实、合理推断、未验证事项、与本次失败无关的背景噪声。

解释阶段默认只读，不修改代码、不创建提交、不自动重跑昂贵测试、不自动部署。

## 失败分类

先判断主因属于哪一类，可同时标注次要原因：

- **实现问题**：代码逻辑、边界条件或配置本身不满足目标。
- **验收/证据问题**：功能可能部分可用，但检查、digest、来源绑定或测试证据不足以证明它正确。
- **环境/资源问题**：依赖、权限、网络、内存、GPU、工具版本等阻止了验证。
- **数据/输入问题**：输入缺失、格式错误、数据冲突或数据质量不足。
- **流程/范围问题**：约束、阶段、重试次数或授权不允许继续。

不要仅凭错误关键词认定为“算法错”；先判断失败发生在哪一层，以及是否真的影响业务结果。

## 固定输出格式

使用中文，按下面顺序输出；没有证据的字段写“未验证”：

### 一句话结论

用一句不超过两行的话说明：失败发生在哪一层、当前能否继续。

### 发生了什么

用时间或流水线顺序描述关键事件，最多 5 步。首次出现技术术语时立即附上白话解释。

### 为什么失败

分别写：

- 直接原因：哪个检查、命令或约束没有通过；
- 根本原因：为什么会出现这个缺口；
- 失败类型：实现、验收/证据、环境/资源、数据/输入或流程/范围。

### 已完成与未完成

明确列出已经验证通过的部分，以及阻止整体通过的部分。不要用“基本完成”掩盖 blocker。

### 对项目的影响

说明是否影响正式代码、生产默认、数据、索引、远程环境、后续 full 测试或提交；没有影响也要明确写出。

### 术语翻译

只解释本次真正出现的术语。格式为：`术语` = 一句白话 + 必要时补充它在本项目中的作用。

### 通俗例子（必填）

必须给出一个与失败机制对应的日常例子，不能只是重复技术定义。优先使用“验收像考试/质检”“digest 像封条编号”“fail-closed 像闸机遇到票据异常就不开门”等短例子，并明确指出例子中的哪个部分对应本次任务。

### 下一步

按优先级给出不超过 3 项行动。每项说明目的和完成标准；如果需要用户决定，明确提出选择点。

### 证据与置信度

列出关键文件、命令或任务记录路径，并标注结论是“已确认”“高概率推断”还是“待验证”。

## 写作规则

- 先用日常语言，再保留括号中的英文或代码标识，避免连续堆砌缩写。
- 用“系统拒绝继续”“检查没有发现篡改”等可理解的动作描述，少用“链路异常”“契约不满足”这类空泛句子。
- 解释“失败”与“没有证据证明成功”的差别；后者不能自动等同于业务功能错误。
- 如果状态为 `blocked`，明确说明“这是保护性停机，不是已经完成”。
- 报告长度以用户能快速读完为准；复杂任务可以展开证据，但保持固定标题顺序。

## 自动接入编排闭环

当本 Skill 被 `single-phase-execution-loop` 或 `multi-phase-plan-orchestrator` 调用时：

1. 在 Reviewer `FAIL`、达到 `max_retries` 或阶段 `blocked` 后生成解释；
2. 解释先于下一轮 retry 展示，但不改变机器可读的 Reviewer YAML、retry 计数或状态文件；
3. 若失败可重试，最后一节给出面向 Executor 的技术动作，同时给用户一个白话版动作；
4. 若达到最大重试或确实 blocked，停止自动推进并把 blocker、影响和通俗例子一起交还用户。

## 最低质量门禁

输出前检查：

- 是否引用了实际证据，而不是只复述错误标题？
- 是否区分了业务逻辑失败与验收/证据失败？
- 是否说明了正式环境是否受到影响？
- 是否解释了本次出现的关键术语？
- 是否包含一个真正帮助理解因果关系的通俗例子？
- 是否明确写出未知信息和下一步？
