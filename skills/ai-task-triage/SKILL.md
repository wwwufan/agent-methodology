# AI 任务诊断与路由

## 定位

回答“当前为什么推进不下去，先补哪一项，交给谁继续”，不是再建一层执行编排。
诊断单位是**当前任务或阻塞点**，不是把整个项目永久标为熟悉/未知。
即使项目熟悉，也可能有局部未知；陌生项目中路径清楚的小任务也可以直接执行。

## 入口与权限

- 新任务无法确定推进方式、执行中出现上述症状，或失败解释后需要重新判断方向时使用。
- 已有明确修复动作或明确下游路由时复用它，不为了流程完整重复诊断。
- 默认只读：读取当前目标、已有上下文、状态和相关证据，不修改业务文件、不建栈、不运行实验、不委托角色。
- 用户只问“为什么/该怎么办”时，到建议为止。已有实施授权时，将诊断交回原调用者，由其在原授权范围内继续。
- 权限、账号、外部依赖、预算上限、用户暂停和阶段审批等硬门禁优先；诊断不能解除它们。

## 诊断方法

先读现有材料，缺证据则标为“未确认”，不要把所有问题重新问用户。
优先复用失败报告中的事实、失败类型和证据指针，不重写一份失败报告。
检查输入和交接时读取 `project-context-brief/references/task-contract.md`，复用其六项输入及质量语义，
不另造表单或强制先调用上下文 Skill。熟悉度与质量要求独立判断，已有充分信息不重复收集。

### 1. 检查连续性

能否说清总目标、当前步骤、未完成分支和返回位置？是否已有可靠记录？
工作量大不等于任务已丢失；已经由推进栈可靠管理的多分支任务，也不需要再建一份状态。
若状态已丢失，先恢复目标和位置，再判断实现路线。

### 2. 检查当前问题的熟悉度

- **熟悉**：有适用的参考实现、已验证路线或已知根因。
- **局部未知**：整体路线清楚，但一个关键决策缺少证据。
- **未知**：当前没有足以支持下一步的可行路线。

区分“答案在现有代码/协议里但尚未读取”和“答案需要实验才能产生”。
人的陌生感、陌生语法或仓库大小本身都不证明需要探索。

### 3. 检查信息充分度

按当前决策需要检查六项职责，不要求每项都写成长文：

- 目标制定：要解决什么，范围与非目标是什么；
- 上下文补充：现状、相关实现和历史决定是否可追溯；
- 约束设计：哪些兼容、风格、依赖、成本或风险限制不能违反；
- 任务拆解：当前一步能否完成并验证，依赖是否清楚；
- 系统决策：哪些选择已有依据，哪些涉及用户的价值取舍；
- 验收：如何知道这一步确实完成。

把缺口分为：已有事实未提供、技术知识待验证、用户取舍待决定。
不要把三者都归为“用户没把提示词写好”。

### 4. 检查可验证性

是否有与目标对应的观察、样例、测试或人工验收方法？
“只要可用”也需要最小可用判据，但不应被扩张成生产级质量要求。
若判据本身依赖效果基线，建议先探索；若只是已知测试尚未执行，交回执行者取证。

## 路由规则

选出一个首要缺口和最小下一步，其余列为条件式后续，不把全部 Skill 串成必经流程。
下表只描述交接职责；各下游的启用判据、预算、授权和退出条件仍以其自身 Skill 为准。

| 证据指向的缺口 | 建议去向 | 交接内容 |
| --- | --- | --- |
| 目标、位置或分支可能丢失 | `campaign-work-stack` | 总目标、已知位置、待恢复分支；由该 Skill 判断恢复或申请启用，不能自动建栈 |
| 已存在的项目事实、约束或验收输入不足 | `project-context-brief` | 当前任务、缺失项、可读取来源 |
| 路线、可行性、根因或效果需要新证据 | `exploration-loop` | 知识问题、现有证据、要解锁的决策；由该 Skill 判断是否探索 |
| 目标或成本、风险、“够好”存在价值取舍 | 用户决策 | 必要选项、影响和已有证据；不把可通过低成本实验解决的技术题甩给用户 |
| 权限、外部资源或停止门禁阻塞 | 原调用者/用户 | 阻塞证据、恢复条件；不以探索或重开任务绕过门禁 |
| 路线、输入、验收充分 | 原执行入口 | 当前可执行步骤；小任务直接执行，需要阶段门禁时才建议阶段编排 |

多个缺口并存时，通常先恢复位置，再补现有信息，再解决真正未知的决策，最后执行。
这是诊断优先级，不是无条件调用链；硬门禁下只给恢复建议。

需要判断编排强度时，交由
`campaign-work-stack/references/orchestration-strength-guide.md`；
其涉及建栈的动作仍受 `campaign-work-stack/SKILL.md` 的启用批准约束。
`guided-goal-orchestrator` 只能由用户显式选择，不能因任务大而自动启用。

## 输出与交接

用简短中文输出以下内容，可合并成几句话，不强制生成文件：

1. **当前判断**：连续性是否可靠、熟悉度、信息是否足够、验收是否清晰；未知项明确标出。
2. **首要缺口与证据**：说明最影响当前下一步的缺口和证据指针，区分事实与推断。
3. **需补职责**：六项职责中当前需要补哪项；已足够的项不重复加工。
4. **最小路由**：先做什么、达到什么条件后交还谁；明确暂时不需要的流程。
5. **继续权限**：原授权内可继续，或必须停下等待哪个用户决定/外部条件。

退出时将这份诊断交回调用者；下游信息补齐后直接回到原执行入口，不默认再跑一次诊断。
已有工作记录时由其拥有者按原流程保存摘要/指针，不另建诊断台账。
在上述输出中合并共享约定的交接信息：具体返回位置、结论与证据适用范围、剩余阻塞及下一步权限。
接收方核对本次解锁的是哪一步；“输入已足够”不是实施许可，也不自动解除暂停或审批门禁。

## 失败解释后的接入与防循环

`explain-task-failure/SKILL.md` 的“解释后的条件式诊断”是失败入口的接线真源。
本 Skill 只消费其事实和证据，不反向调用失败解释。

- 同一任务、同一组证据只诊断一次；被内外层编排同时调用时复用已有结论。
- 仅在目标/范围改变、出现会推翻旧路由的新证据，或当前路线暴露出新的缺口时重新诊断。
- 不清零 retry、不重开预算、不改 Reviewer 结论、不自动恢复 blocked/暂停任务。
- 下游 Skill 不可用时明确报告缺失，交回调用者；不能声称已经调用或创建并行替代流程。

## 模型能力归因

模型限制可以是候选原因，但不能把失败直接等同于模型不行，也不能预设所有任务模型都能完成。
先排查输入、范围、验收和环境。只有这些因素已有证据支持充分，且缩小到可验证的最小任务后仍表现出稳定失败，
才报告“疑似当前模型/工具组合的能力边界”及证据；不把它说成已经证明的唯一原因。
不要为了做出这项归因而额外发起未获授权或没有停止条件的重复实验。
