# 编排强度选择指南

本文件是真源，位于 `<本 skill 目录>/references/orchestration-strength-guide.md`（`<本 skill 目录>` = campaign-work-stack 的 skill 根目录），
由 `campaign-work-stack/SKILL.md` 引用：`survey` 选出大事后、决定用多强的编排时读。

## 核心立场：粒度不可预判，只能自适应

任务的大小与复杂度**原则上无法在开工前判定**——复杂度是在做的过程中显现的。
一个看起来「单窗口就能做完」的任务，做到一半发现要改契约，就变成多阶段了。

所以不要追求「选对粒度」，要追求**改粒度便宜**：

- 栈已启用时，先粗压一帧；没有栈时先用当前任务描述表达，不因此自动建栈
- 太大 → 已有栈时 `push --parent` 拆子帧；已做的工作不丢，父帧转 `suspended`，子帧关掉后自动恢复；无栈先拆任务描述
- 不成立 → 已有栈时 `pop --terminal wontfix|parked` 并写理由（留痕于 `pop_log`）；无栈在既有记录中说明处置
- `MAX_DEPTH=4` 与「超深说明帧定义太粗，应先拆分或 parked」是防止无限细分的刹车

**升级路径单向便宜**：栈 → 单阶段 → 多阶段，随时可升。
**降级很贵**：一旦建了 Goal、落了不可变快照，就退不回去。

## 默认策略

> **编排强度按需升级；栈的启用由用户决定 —— 代理评估复杂度后 `propose` 申请，未获批准不得创建；栈已存在则直接接线、零提问。**

两条理由，方向相反但都成立：

- **不轻易加编排**：编排有仪式成本。给改三行代码的任务套三角色门禁是纯浪费
  （`single-phase-execution-loop` 自己写明「不适用：一次性小改、无需 reviewer 门禁的简单任务」）。
- **不轻易加栈**：栈也有**维护与注意力成本**——一旦启用，每轮都要 `show`/`verify`、
  关帧要 `pop` 四段回看、收工要 `retro`。更关键的是栈绑的是**总目标**：为一个临时小活创建栈，
  会把这个 campaign 的复盘数据污染成噪音。

所以旧版「总是先上栈（免费、无损）」的说法**已作废**；「按编排身份自动启用」的中间版本**同样作废**
——身份不等于粒度，受控目标模式也可能只跑一个很小的阶段，而新建的空栈 `verify` 是 PASS 的，
没有任何机械信号会告诉你「这个栈本来不该存在」。现行口径：栈**已存在**就直接接线；
**不存在**则由代理按六维信号评估（见 [activation-and-recovery.md](activation-and-recovery.md)），
命中 ≥2 就 `propose` 打印申请卡，**用户批准才创建** —— 提议不等于自动创建。

## 信号表

| 信号 | 含义 | 升级到 |
| --- | --- | --- |
| 一句话说不清完成判据 | 任务太大或目标模糊 | 先澄清目标/拆任务；已有栈才拆帧，不要急着上编排 |
| 中途要做不可逆决定（commit / 删文件 / 改契约 / 改 schema） | 需要门禁 | 单阶段编排（Reviewer） |
| 预计跨会话 / 跨天 / 上下文可能被压缩 | 必须状态外化 | 栈 + 台账（**评估后向用户申请**，未获批准不得创建；已存在则直接接线） |
| 有多个各自可独立验收的交付物 | 天然分阶段 | 多阶段编排 |
| 失败回滚成本高 | 需要独立复核 | 单阶段编排以上 |
| 路线 / 阶段边界 / 验收标准要由用户拍板 | 需要人工门禁 | 受控编排 |
| **以上都没有，就是一次性小改** | — | **直接做，别加仪式** |

## 五种强度的对照

| 强度 | 用什么 | 状态真源 | 谁解锁下一步 | 推进栈 |
| --- | --- | --- | --- | --- |
| 直接做 | 无 | 无 | — | **不启用**（除非用户声明，或 `propose` 获批准） |
| 栈推进 | `campaign-work-stack` | `active-work-stack.json`（`workstacks/<campaign>/`，v4 起**纳入 Git**、绑台账、跨轮续用） | 用户 `activate` 选帧 | 本体；由**用户声明或批准申请**而起 |
| 单阶段门禁 | `single-phase-execution-loop` | `progress_tracker` + 角色报告 | Reviewer PASS 且阶段收尾完成，交还用户 | **只接线不创建**：栈已存在才 `capture`/`pop` |
| 多阶段自动 | `multi-phase-plan-orchestrator` | `execution-plan.md` + `progress.md` | Reviewer PASS 且内层收尾完成，按原授权进 N+1 | **已存在则接线；不存在则 `propose` 申请，批准才建** |
| 多阶段受控 | `guided-goal-orchestrator` | `goal-ledger.md` + 不可变快照(SHA-256) | **用户逐阶段批准** | **同上**（启动与恢复都先 `stacks` 探测） |

后两者**互斥**：受控编排明文禁止调用多阶段自动编排，因为「PASS 自动进 N+1」
与「阶段批准权归用户」语义冲突，不是风格偏好。

## Goal 与阶段粒度的结构约束（F-016 核实结论，供重开时引用）

Codex 的 Goal 是**独占、串行、不可暂停**资源：存在未完成 Goal 时 `create_goal` 直接失败，
`update_goal` 只能置 `complete` 或 `blocked`。

**受控编排「一 Goal 一阶段」由三条硬约束强制，不可放宽：**

1. **Goal 仅三态**（active / complete / blocked），装不下 `awaiting_user_approval`
   这个第四态；受控编排的映射是「Goal complete = 已交付评审候选，≠ 阶段已获批准」，
   该映射只在一 Goal 一阶段时成立。
2. **Goal 必须绑定阶段快照的 SHA-256**，而未来阶段的快照要等用户在计划模式确认方案后才生成
   ——无法绑定一份尚不存在的快照。
3. **Goal objective 不可变**（`update_goal` 只改状态）。路线一变正文即失效，只能收口重开；
   跨多阶段的 Goal 会让任一路线变更作废整个 Goal，包括已批准的阶段。

**自动编排下三条均不成立**（无阶段间等待态、`execution_plan` 启动即含全部阶段、
路线变更只需更新 `progress.md`），故「单 Goal 覆盖多阶段」结构上可行。

**但按用户 2026-09-18 判定：先不做。** 理由——这不是「值不值得做」的问题，而是
「用户对问题粒度大小的判断」问题；粒度判断错时，更大的编排容量只会把错误放大。
着力点在本指南（判断依据），不在扩容。详见栈帧 F-016 的 `parked` note。

## 栈的绑定对象（回答「栈跟着什么走」）

**跟着总目标（campaign）走，与 `goal-ledger.md` 一对一绑定**；不跟轮次、不跟对话窗口、不跟阶段 Goal。
换窗口、换阶段、开新一轮都**续用同一个栈**，`retro` 复盘的是整个 campaign 的弯路。

- 不绑 Goal：Goal 独占、串行、不可暂停，收口即释放；而阶段间收尾工作恰恰发生在 Goal 释放之后。
- 不绑 phase：装不下跨阶段帧与不属于任何阶段的工具自建帧。
- 不绑轮次/窗口：一轮的边界只在用户脑子里，跨窗口即断 —— 那正是要消灭的失败模式。

启用策略见上表「推进栈」列；`bound_ledger` / `activation` 字段与机械校验见
[stack-schema.md](stack-schema.md) 的「绑定字段（v3 新增）」。

## 用户决策的三个嵌入点

用户是 AI 无法自行计算的**路由函数**：优先级、风险偏好、业务口径、什么算「够好」，
都不能仅凭代码推定。下面三个位置需要用户决策；同一任务已有有效授权时不为恢复接线重复询问，
也不要求用户逐帧重批已批准的自动多阶段计划。原暂停、范围变更与受控审批门禁仍有效：

| 嵌入点 | 所在层 | 用户决定什么 |
| --- | --- | --- |
| `survey` 选单 | 栈 | 从长期池挑哪件大事进本轮 |
| `activate` 选帧 | 栈 | 本轮内先推哪一帧（`actor=user` 的方向切换，区别于 `actor=dfs` 的自动抢占） |
| `awaiting_user_approval` | 受控编排 | 该阶段交付算不算过、路线要不要改 |

## 一句话总结

多阶段编排 / 目标模式 / 栈，三者的共同本质是**把状态从上下文窗口内搬到窗口外**——
不是扩大白板，而是给你笔记本并允许你擦白板。窗口大小从未改变，改变的是**对窗口的依赖**。
所以目标是「分次解决但不断线」，而不是「一次吞下更大的问题」。
